# Verse Bot — техническая архитектура

> Этот файл является текущим источником истины по технической архитектуре и принятым ограничениям `verse-bot`. Продуктовый roadmap и межпроектные планы ведутся отдельно.
>
> README и публичная документация поддерживаются отдельно и должны соответствовать этому документу. Старые рабочие заметки из `ImpBot.md` не являются актуальной спецификацией.

## 1. Текущая цель

`verse-bot` — монорепозиторий с переиспользуемыми TypeScript-пакетами для создания и запуска Telegram- и VK-ботов на VPS.

На первом этапе проект ориентирован на собственные приложения:

- `apps/imp-bot` — интеграционный бот-пример и основной полигон тестирования пакетов;
- `/home/v/Projects/doubletardigrade-bot/` — отдельный действующий VK-бот, который позже должен быть частично или полностью переведён на пакеты `verse-bot`;
- `/home/v/Projects/flag-connect/` — Telegram Mini App, уже использующий `@verse-bot/miniapp`.

Долгосрочно проект может стать открытым фреймворком, но текущая цель скромнее: сделать небольшой набор пакетов, который реально уменьшает сложность разработки и поддержки собственных ботов.

## 2. Основной принцип

Общей должна быть **бизнес-логика**, а не абсолютно весь код.

Команды должны работать через Telegram и VK настолько одинаково, насколько это позволяют платформы. Различия должны находиться на границе адаптеров и presentation-слоя.

Хороший результат:

```text
одна бизнес-логика
+ общий контекст и middleware
+ платформенные адаптеры
+ платформенный UI там, где он действительно различается
```

Не требуется и не следует добиваться полностью одинакового API для:

- Telegram rich messages;
- VK-сообщений;
- inline keyboard и VK payload;
- callback queries;
- Telegram Mini App;
- загрузки и отправки медиа;
- особенностей групповых чатов.

## 3. Актуальные пакеты

### `@verse-bot/core`

Нейтральное ядро:

- общие типы;
- `UniversalContext`;
- middleware;
- общие проверки и ошибки;
- callback capability-контракт для ответа на callback и редактирования исходного сообщения;
- исходный payload события и общий асинхронный контракт проверки администратора;
- платформонезависимые контракты.

`core` не должен зависеть от Telegram-специфичного форматирования.

### `@verse-bot/telegram`

Telegram-адаптер:

- runtime на `grammY`;
- Telegram-команды и события;
- Telegram-клавиатуры;
- Telegram-specific middleware;
- callback-запросы с опциональным обработчиком исходного payload;
- callback answer/edit и fallback-обработчик `onMessage` для произвольных входящих updates;
- асинхронный `checkAdmin` для Telegram-ролей или дополнительных администраторов;
- поддержка сообщений, совместимых с `tg-rich-messages`.
- PostgreSQL подключается опционально через нейтральный `BotDatabase` из `@verse-bot/core`.

Сам `@verse-bot/telegram` не обязан напрямую зависеть от `tg-rich-messages`: пакет принимает нейтральный renderable message-контракт, а форматирование может находиться в приложении или отдельном Telegram-слое.

### `@verse-bot/vk`

VK-адаптер:

- runtime на `vk-io`;
- VK-события и команды;
- VK-клавиатуры и payload;
- callback-события `message_event` с опциональным обработчиком исходного payload;
- ответ на VK callback, редактирование callback-сообщения и fallback `onMessage`;
- кнопки callback-типа с данными и цветами VK;
- дополнительный API-клиент `userApi` для второго токена и отправка существующих photo attachment ID;
- асинхронный `checkAdmin` для ролей сообщества;
- обычные строковые сообщения и ссылки в VK-разметке.
- PostgreSQL подключается опционально через нейтральный `BotDatabase` из `@verse-bot/core`.

Полноценный аналог Telegram rich messages для VK не является целью. VK в текущем проекте использует обычные строки и поддерживаемую API-разметку ссылок.

### `@verse-bot/miniapp`

Независимый пакет утилит для Telegram Mini App с framework-agnostic API и Angular-интеграцией.

Пакет уже используется проектом `flag-connect` и является одним из наиболее практически проверенных пакетов.

### `@verse-bot/postgres`

Текущий пакет работает только с PostgreSQL. Абстракция над произвольными базами данных пока не является целью.

Пакет переименован из прежнего `@verse-bot/db` в более честный `@verse-bot/postgres` до следующей публичной серии версий. Это не добавляет новую сущность, а точнее описывает уже существующую реализацию.

Пока PostgreSQL — осознанный конкретный выбор для собственных проектов.

### `tg-rich-messages`

Самостоятельный пакет, независимый от `verse-bot`, только для Telegram rich messages.

Он не должен находиться в нейтральном `@verse-bot/core`. Его потребителями могут быть:

- `@verse-bot/telegram`;
- приложения на `grammY`;
- другие Telegram-проекты.

### Исторические пакеты

- `@verse-bot/shared` — прежнее имя/слой, заменённый `@verse-bot/core`;
- `@verse-bot/md-format` — предыдущий подход к форматированию, заменённый самостоятельным `tg-rich-messages`.

Опубликованные версии не удаляются без отдельной причины. Новые проекты не должны строиться на этих пакетах.

## 4. UniversalContext

`UniversalContext` нужен для общих возможностей:

- идентификатор пользователя в текущей платформе;
- опциональный внутренний идентификатор пользователя из БД;
- идентификатор чата/peer;
- платформа;
- текст команды;
- ответ текстом или renderable message;
- отправка результата;
- общие данные middleware.

На callback updates контекст дополнительно предоставляет `callback.data`, `callback.messageId`,
`callback.answer()` и `callback.editMessage()`. Эти операции являются capability callback-события,
а не частью контекста каждого сообщения.

Контекст не должен превращаться в объединение всех API Telegram и VK.

Если возможность есть только у одной платформы, она должна оставаться платформенной или выражаться через отдельную capability, а не через искусственно универсальное поле.

### Rich messages

Telegram использует `tg-rich-messages`. VK использует строки.

Целевое направление:

```text
@verse-bot/core   — без зависимости от tg-rich-messages
@verse-bot/telegram — может использовать tg-rich-messages
@verse-bot/vk — работает со строками
```

Общие команды должны по возможности формировать нейтральный текст. Telegram-специфичное форматирование должно добавляться в Telegram presentation-слое или Telegram-specific коде.

## 5. `apps/imp-bot`

`apps/imp-bot` — интеграционный бот-пример и основной полигон тестирования пакетов.

Он должен проверять настоящую цель проекта: одну прикладную логику в Telegram и VK, насколько это возможно.

### Что должно быть общим

- бизнес-правила;
- проверки пользователей и прав;
- работа с PostgreSQL;
- выбор и изменение данных;
- логирование действий;
- общие сценарии команд.

### Что может различаться

- получение данных из платформенного события;
- клавиатуры;
- callback/payload;
- отправка медиа;
- форматирование;
- особенности чатов;
- платформенные функции вроде Telegram Mini App или VK-specific API.

## 6. `doubletardigrade-bot`

Это отдельный действующий VK-бот. Его тихоходки и квизовая бизнес-логика принадлежат приложению и не переносятся в пакеты `verse-bot`.

VK-адаптер предоставляет общие механизмы, которые это приложение может использовать при необходимости: обработку обычных сообщений, асинхронную проверку ролей, callback answer/edit, дополнительный API-клиент и отправку существующих photo attachment ID.

Связывание Telegram- и VK-идентичностей не реализовано. Если оно понадобится, объединять аккаунты можно только после явного подтверждения пользователем; автоматически сопоставлять по имени, username или аватару нельзя.

## 7. База данных

На текущем этапе используется PostgreSQL.

Не следует создавать абстракцию «любой базы данных» без реального потребителя. Если позже появится необходимость в SQLite, другой SQL-БД или отдельном storage, это будет отдельное решение на основании практической потребности.

## 8. Storage и Garage

Garage подходит как S3-compatible инфраструктура для будущего хранения изображений и других объектов на VPS.

Но storage пока не входит в MVP `verse-bot`:

- текущие проекты могут работать без него;
- изображения `doubletardigrade-bot` сейчас представлены VK attachment ID;
- ресурсы `flag-connect` входят в статическую сборку;
- Garage не заменяет PostgreSQL;
- публичная раздача объектов из Garage требует отдельного HTTP-слоя.

На текущем этапе не создавать storage-абстракцию и Garage-пакет без реального сценария использования.

## 9. CLI

`create-verse-bot` — минимальный CLI для генерации проекта, который сейчас проходит проверку перед первой публикацией.

CLI не следует расширять, пока не проверены базовые сценарии:

1. пакеты стабилизируются;
2. структура несколько раз проверится на реальных проектах;
3. станет понятно, какой boilerplate действительно повторяется;
4. будет определён минимальный рабочий проект Telegram/VK.

CLI должен фиксировать только уже проверенную структуру проекта и не добавлять новые архитектурные решения сам по себе.

Целевой сценарий в будущем:

```text
create-verse-bot my-bot
cd my-bot
npm install
npm run build
npm run dev
```

Этот сценарий должен работать в чистой директории до того, как CLI можно будет считать полезным.

## 10. Публикация npm-пакетов

Опубликованные версии `0.x` считаются ранними экспериментальными релизами, а не обещанием стабильного API.

Перед следующими публикациями каждый пакет должен быть проверен вне root workspace. Для Node-пакетов это автоматически проверяется командой:

```bash
npm run test:packages
```

Проверяются:

- зависимости в собственном `package.json`;
- отдельная сборка;
- содержимое `npm pack`;
- установка tarball в чистый consumer-проект;
- generated declarations и exports;
- импорт `@verse-bot/core`, `@verse-bot/postgres`, `@verse-bot/telegram`, `@verse-bot/vk`;
- импорт собранного `@verse-bot/miniapp`.

README и package metadata проверены для текущего набора пакетов; перед публикацией нужно повторить проверку tarballs в чистом consumer-проекте.

Не публиковать `1.0.0`, пока пакеты не проверены на реальных проектах и их публичный API не перестал заметно меняться.

## 11. Правила, относящиеся к этому проекту

- Не создавать в `verse-bot` абстракции без реального потребителя.
- Общую бизнес-логику Telegram и VK переиспользовать там, где это действительно удобно, но не скрывать реальные различия платформ.
- Telegram rich messages не должны попадать в нейтральное `@verse-bot/core`.
- Каждая runtime-зависимость должна быть объявлена в пакете, который её импортирует.
- Каждый публичный пакет должен работать вне monorepo и без скрытого root hoisting.
- Не проектировать API под отложенные или гипотетические возможности раньше реальных сценариев.
- Изменения в архитектуре проверять на `apps/imp-bot` и, где применимо, на `doubletardigrade-bot`.
